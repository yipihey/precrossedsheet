# WebGPU acceleration assessment

## Recommendation

Do not add a GPU backend based on the current timing data alone. A scratch-only native stage profile now shows that, for the measured 3D wave requests, direct continuous Fourier modes, tangent modes, and finite-difference checks dominate. This makes that combined measurement path the best first investigation target; it does not establish the cost of each sub-operation inside it. The project’s `app/js/viz/gpu.js` is currently only a canvas CSS-size helper; there is no WebGPU compute path.

The [benchmark log](benchmarks.md) records whole-run native measurements. The stage profile below used a temporary instrumented copy and one sequential run per case. Instrumentation and machine-specific timings are exploratory evidence, not representative throughput claims. In particular, the direct-mode stage combines the LPT and PM simplex integrals, tangent propagation, and finite-difference checks, so a follow-up should instrument those operations independently and repeat each run before selecting a kernel.

## Native stage profile

The profile ran on an Apple M5 Max MacBook Pro (18-core arm64, macOS 26.7) with `rustc 1.98.1`, release mode, offline dependencies, and a dedicated `/private/tmp` Cargo target. Both requests used 32 time steps, scale factor 0.25, order 4, seed 7, wave initial conditions, fraction 0.5, smoothing 0.03, $Ω_m=0.315$, $Ω_b=0.049$, $h=0.674$, $n_s=0.965$, $σ_8=0.811$, box size 300 $h^{-1}$ Mpc, initial smoothing 14 $h^{-1}$ Mpc, and cutoff 3. The lattice, exact-deposit mesh, and force mesh were all $n^3$ for each case. Each was run once; there was no warm-up or repeated-run estimate.

The direct-mode group was 93.0% and 92.8% of the summed pre-serialization stage times in these two single runs. It comprises continuous simplex Fourier integration for LPT and PM, analytic amplitude tangents, and finite-difference checks for selected modes. It is therefore the measured priority for finer profiling and a possible prototype: batch independent simplex/mode work while retaining the continuous simplex integral, explicitly propagate the JVP, and use a deterministic reduction. Do not substitute cell-center sampling. WGSL's portable baseline is `f32`, whereas the native Fourier/tangent paths use `f64`; a GPU prototype will need an explicit error budget and must handle coincident/repeated phases with the same stable limiting formulas as the CPU path. Fixed reduction order (or quantified reduction-order error) is required for reproducibility and conservation checks.

The stage totals are from the instrumented copy and can include timer overhead; external wall time is measured separately and is not a denominator for the percentages. As a rough consistency check, earlier uninstrumented aggregate runs took about 14.9 s for 3D32 and 120 s for 3D64, so instrumentation/build-state/run-to-run differences are material. Browser measurements must include adapter/device, compilation, upload, dispatch, synchronization/readback, and end-to-end latency. ## Kernel candidates and constraints

| Core path | GPU fit | Main risk |
|---|---|---|
| Continuous simplex Fourier modes and JVPs (`direct.rs`, `tangent.rs`) | The combined group dominates these measured runs. Simplex/mode contributions are independent before a deterministic reduction, making batched evaluation a plausible first prototype. | The current profile does not separate transforms, tangents, or finite-difference checks. Preserve the continuous element integral, analytic tangent, stable coincident-phase limits, fixed-mass normalization, and deterministic or error-bounded reductions. Native paths use `f64`; WGSL baseline arithmetic is `f32`. |
| Fourier-space LPT source algebra (`lpt.rs`, `fft.rs`) | Regular pointwise tensor invariants, Poisson factors, and repeated transforms offer substantial parallel work. A GPU-resident sequence could avoid repeated host transfers. | The current FFT and spectral arithmetic use complex `f64`; baseline WGSL arithmetic is `f32`. A portable FFT implementation and its normalization, Hermitian/Nyquist conventions, and error budget need independent verification. The measured direct-mode group does not establish this as the bottleneck. |
| PM CIC deposit/force/gather (`nbody.rs`) | Particle deposition, mesh force, and gather are naturally parallel and repeat every step. | CIC deposition has write collisions. Baseline WGSL atomics operate on integers, so floating-point mass accumulation needs an explicitly validated strategy such as sorted or tiled reduction; parallel reductions also change summation order. The full path also requires a 1D–3D FFT Poisson solve and analytic tangent propagation. Uploading and reading back every step would erase much of the benefit. |
| Exact simplex clipping (`sheet.rs`, `observables.rs`) | The number of elements is large and each element is independent before accumulation. | Cell intersections, polygon/polyhedron clipping, and candidate-cell counts are irregular. Floating-point boundary decisions and concurrent reductions can lose the conservation and positivity guarantees. It is the highest-risk port and must not be replaced by center sampling or stochastic rasterization under an “exact” label. |
| Smoothing, spectra, and display | Grid operations have regular work; display-only rendering can benefit without changing physics. | Smoothing/spectra depend on FFT; visual acceleration does not reduce numerical compute. Keep display-decimated geometry separate from every scientific estimator. |

The first prototype should target the measured direct-mode group by separating and profiling continuous mode integration, tangent propagation, and finite-difference checks. A plausible candidate is batched simplex/mode evaluation with explicit analytic JVPs and deterministic reductions; keep the CPU continuous integral as the oracle and fallback. Consider making the finite-difference self-check opt-in or caching it only if product semantics allow and after measuring its standalone cost. Do not report that as a speedup before validation. The facade evaluates six first-axis modes on four trajectory configurations per mode: LPT, the two finite-difference perturbations, and PM. Its power-only finite-difference calls currently use the JVP routine with a zero direction; skipping zero phase-direction work or adding a validated value-only path is a concrete CPU optimization to measure alongside a GPU prototype. Keep PM and LPT candidates available if finer profiles show they matter. Avoid crossing the CPU/GPU boundary repeatedly: upload shared state once, execute a staged resident pipeline, and read back only arrays needed by the CPU-only estimator.

WebGPU is a secure-context API with adapter/device acquisition and device-specific limits; request only capabilities actually needed and query the chosen device’s limits rather than assuming a machine-independent memory budget. The specification documents bounded storage-buffer sizes and mapping behavior, so large 3D state may need chunked bindings/dispatches and asynchronous readback. See the [W3C WebGPU specification](https://www.w3.org/TR/webgpu/) and [WGSL specification](https://www.w3.org/TR/WGSL/). WGSL’s floating-point contract is IEEE-754-based with GPU-oriented portability limits, not a promise of cross-device bitwise identity. GPU output therefore needs numerical tolerances, and a device or shader change must be represented in exported run metadata.

## Validation gates

1. Keep Rust CPU as the oracle and fallback. Compare each isolated GPU stage on analytic fixtures and saved 1D/2D/3D requests; cover odd/even grids, periodic boundaries, zero modes, Nyquist handling, Hermitian pairing, and the same seeded physical modes across refinements.
2. Compare the complete output at fixed inputs and epoch: positions, density, direct modes/power, PDFs/quantiles, PM crossing bracket, and diagnostic Jacobians. Set per-observable absolute and relative tolerances from CPU refinement and physical convergence studies; do not choose a looser tolerance merely to pass the GPU.
3. Require global mass conservation, nonnegative stream density, translation invariance, and unchanged crossed-element mass accounting. Exercise near-degenerate simplices and cell-boundary cases. Exact clipping remains CPU until a GPU algorithm passes independent geometric fixtures and the same conservation/error contract.
4. Validate derivatives separately. WGSL does not provide automatic differentiation for this pipeline: carry the existing analytic tangent explicitly through every GPU operation. Check the tangent against centered finite differences at fixed cosmology, clock, and mesh, including CIC cell transitions and smooth branches. The exact-clipped-density shape derivative is not currently implemented; a GPU port of clipping does not create one.
5. Compare full end-to-end browser latency, including adapter startup, pipeline compilation, upload, dispatch, synchronization/readback, and fallback. Publish speedups only for named hardware/browser/workloads, and retain CPU results as the correctness route when WebGPU is unavailable or fails validation.

This is a profiling and validation plan, not a claim that this repository currently has GPU-accelerated scientific kernels.
